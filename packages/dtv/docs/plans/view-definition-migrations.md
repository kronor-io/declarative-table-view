# View definition changes and user data — implementation plan

Status: agreed design, implementation in progress (branch `view-definition-migrations`).
Phases 1–3 done; see the "as built" sections at the end. User docs: `docs/view-migrations.md`.

## Problem

User data (saved filters, persisted filter state, hidden columns, column order, soon sorting, shared URLs)
is keyed by ids from the view definition and shaped by its filter expressions. When a definition changes,
today's behaviour is:

| Change | Result today |
|---|---|
| Filter id renamed | State silently lost |
| `and`/`or` child added/removed | Arity check fails, filter reset |
| Children reordered, same arity | **Values silently swap** |
| Control type changed, enum/operator values renamed | **Stale value kept and queried** |
| Field / transform semantics changed (e.g. major → minor units) | **Value silently means something else** |
| Column renamed | Hidden column reappears |
| View id renamed | Whole view's data orphaned |

The silent cases are the dangerous ones.

## Vocabulary

| Term | Meaning |
|---|---|
| **User-data-level migration** | dtv's storage format changed. Versioned by global `formatRevision`, shipped with dtv. JSON → JSON, **never needs a view definition**. |
| **View-level migration** | A view definition changed. Versioned per view by `definitionRevision` (integer), generated by the CLI in the app. Uses only its own from/to snapshots, never the live definition. |
| `UserDataWithUndecodedViews` | Result of stage 1: everything outside views fully decoded, each view an `UndecodedViewData`. |
| `UndecodedViewData` | One view's data, validated against dtv's storage format, not yet decoded against its view definition. Nested: `UndecodedSavedFilter`, `UndecodedFilterState`, `UndecodedFilterFormState`, `UndecodedFilterValue`. |
| **Definition id** | The literal id in `DSL.view({ id })`. Identifies a definition, its snapshots and its migrations. |
| **Instance id** | The `id` of a `View` at runtime; may be derived from the definition id (`…-credit`, `…-${orderId}`, `${entity}-history-list`). User data is keyed by instance id. |
| **Projection** | The normalized part of a definition that persisted data depends on. |
| **Snapshot** | A projection committed as code (`as const`), one per `definitionRevision`. The latest snapshot is the lock. |

## Data model

```ts
type UndecodedFilterValue =
    | { type: 'empty' }
    | { type: 'value'; value: Json }
    | { type: 'legacy'; raw: Json }          // pre-2026-03-26 raw leaf, interpreted in stage 2
type UndecodedFilterFormState =
    | { type: 'leaf'; value: UndecodedFilterValue }
    | { type: 'and' | 'or'; children: UndecodedFilterFormState[] }
    | { type: 'not'; child: UndecodedFilterFormState }
type UndecodedFilterState = Record<string, UndecodedFilterFormState>
type UndecodedSavedFilter = { id; name; view; createdAt: string; state: UndecodedFilterState }
type ViewPreferences = { columnOrder; hiddenColumns; rowsPerPage; syncFilterStateToUserData }
type UndecodedViewData = ViewPreferences & {
    definitionRevision: number              // 1 when absent
    persistedFilterState: UndecodedFilterState | null
    savedFilters: UndecodedSavedFilter[]
}                                           // loose: unknown fields survive a round trip
type UserDataWithUndecodedViews = { formatRevision; revision; preferences; views: Record<ViewId, UndecodedViewData> }

// in memory (existing, extended)
type UserData = { …; views: Record<ViewId, ViewData>; retainedViews: Record<ViewId, UndecodedViewData> }
```

- `retainedViews`: views this app instance does not define (the normal case: one blob holds every view of
  every page), views at a newer `definitionRevision`, views whose decoding failed. Re-encoded unchanged.
  Replaces `baseViews`/`mergeViewsJson`.
- Shared URL payload becomes `{ view, rev, state }`; a bare map is legacy (`views[0]`, revision 1,
  `FilterValue.fromObject` heuristic, otherwise a `legacy` leaf).
- Types are inferred from in-house codecs (`framework/user-data/codec.ts`) so decoder and type cannot drift.
  Decode errors carry a path (`views["x"].savedFilters[2].state.amount.children[1]`).

## Pipeline

```
read:   unknown JSON
          → user-data-level migrations (JSON → JSON)
          → decodeUserData → UserDataWithUndecodedViews        (failure: manager read-only, as today)
          → per view known to this App instance:
              stored definitionRevision > current → retainedViews
              view-level migrations (stored revision → current)
              decodeViewData(undecoded, view): rehydrate against schema, ISO → Date, legacy → FilterValue,
                  validate static things (operators ∈ operators, column ids exist, sort column sortable)
              failure → error toast, defaults in memory, original kept in retainedViews until written
          → aggregated reset notice per view
          → persist once if any migration changed anything
write:  encodeViewData(viewData, view): omit empty filters, Date → ISO, stamp definitionRevision
        → merge retainedViews → JSON
```

All read paths use it: initial `synchronize`, `refreshFromLocalStorage` (storage events), remote load.

**Data-driven values are never destructively validated.** Dropdown/multiselect items often come from the
database (subsidiaries, currencies, reasons). A stored value missing from the current items is kept
(today's behaviour). A failed options fetch must not wipe saved selections.

## User-data-level migrations

- Rewrite the four existing steps as JSON → JSON:
  - legacy `dtvSavedFilters` import: move entries without parsing (entries for unknown views are now kept);
  - leaf ADT step: wrap legacy leaf values as `{ type: 'legacy', raw }`;
  - the two preference steps are already schema-free.
- New step: add `definitionRevision: 1` to every view. Bumping `formatRevision` makes stale tabs on older
  dtv read-only instead of carrying stale data forward.
- Rule: a user-data-level step that needs a view schema is a view-level migration in disguise.

## View-level migrations

### Projection

```ts
type ControlProjection =
    | { type: 'text' | 'number' | 'date' | 'custom' | 'dropdown' | 'multiselect' }   // no item values: data-driven
    | { type: 'autocomplete'; multiple: boolean }
    | { type: 'customOperator'; operators: readonly string[]; valueControl: ControlProjection }
type FilterProjection =
    | { kind: 'leaf'; cmp: LeafFilterExpr['type']; field: FilterField; control: ControlProjection }
    | { kind: 'and' | 'or'; children: readonly FilterProjection[] }
    | { kind: 'not'; child: FilterProjection }
type ViewProjection = {
    definition: string; revision: number
    filters: Record<string, FilterProjection>
    columns: Record<string, { orderBy: string | null }>
    transformHashes?: Record<string, string>   // check-time warnings only
}
```

Excluded: labels, `initialValue`, item values, renderers, filter groups, `staticConditions`, row expansion.
The projection must not depend on factory arguments (true for finance once the above are excluded).

### Builder (typed against snapshots; failures reported as `DslTypeError`)

| Op | Constraint | Schema side | State side |
|---|---|---|---|
| `renameFilter(a, b)` | `a ∈ From`, `b ∈ To`, same shape | rename key | move state |
| `keep(id, { because })` | in both, state-compatible | take To | identity |
| `reset(id)` | `id ∈ From` | take To | drop (reported) |
| `drop(id)` | `id ∈ From \ To` | remove | remove |
| `mapValues(id, fn)` | `fn: Json → Json \| DROP` | — | rewrite leaf values |
| `mapOperators(id, map)` | exhaustive over removed operators | rewrite | rewrite |
| `custom(a, b, fn)` | `fn: UndecodedFilterStateFor<From[a]> → …For<To[b]> \| RESET` | take To | `fn` |
| `renameColumn` / `dropColumn` / `resetSort` | column ids typed | | hidden/order/sort |
| `renameView(fromInstanceId)` | | | move data (literal-id instances only) |
| `todo(msg)` | **type error** | | runtime: like `reset`, logs error |

Coverage rule: replaying schema sides over the From snapshot must equal To exactly, except additions.

### Wiring and layout

- `View.migrations?: ViewMigrationChain` passed via `DSL.view({ …, migrations })`. Survives `{ ...view, id }`
  spreads, so derived instance ids are covered. Current revision = `migrations?.latest.revision ?? 1`.
- JSON views: new `viewMigrations` runtime section, referenced as
  `"migrations": { "section": "viewMigrations", "key": "…" }`.
- Generated files next to the view (located through typegen's scan, `ViewInfo.sourceFile`), or under
  `definitions.migrationsDir`:
  ```
  migrations/<definition>/v1.snapshot.ts   export const v1 = {…} as const satisfies ViewProjection
  migrations/<definition>/v2.ts            export default defineMigration(v1, v2, m => […])
  migrations/<definition>/index.ts         (generated) export default defineChain([...])
  ```
- On first generation the CLI prints the one line to add to `DSL.view({ … })`; it never edits view sources.

### Runtime safety

- Dev: live projection ≠ latest snapshot → console error "run `dtv definitions snapshot`".
- Prod, stale chain: reset filters whose projection differs from the latest snapshot, log error.
- No chain: today's behaviour (plus static validation), dev warning.

## CLI

- Config `views: { entry, migrationsDir? }`. The entry default-exports `Record<definitionId, View>`, calling
  factories with placeholder arguments:
  ```ts
  export default {
      'journal-list': journalListDtvView({ currencies: [], subsidiaries: [] }),
      'history-list': historyDtvView({ entityId: '0', entityLog: 'JournalLog' }),
  }
  ```
  `check` cross-checks against typegen's static scan, so a new `DSL.view` missing from the entry fails.
- Loading: through Vite's `ssrLoadModule` with the project's Vite config (aliases, `?raw`, styles); `tsx`
  fallback for projects without Vite.
- `dtv definitions snapshot [--view] [--interactive] [--manual <reason>] [--renamed-from]`

  | Diff | Generated |
  |---|---|
  | additions, label / `initialValue` / item changes, operator added | nothing |
  | filter removed, no candidate | `drop` |
  | removed + added filter of same shape | `todo` (rename / drop) |
  | arity / kind / control type changed, autocomplete `multiple` toggled | `reset` |
  | `cmp` or `field` changed, same control | `todo` (keep / reset) |
  | operators removed | `mapOperators` with `todo` per removed operator |
  | column removed / removed + added / `orderBy` changed | `dropColumn` / `todo` / `resetSort` |
  | definition disappeared + new one appeared | requires `--renamed-from` |
  | no diff, `--manual` | new revision, empty op list to fill (enum renames, semantic changes) |

- `dtv definitions check` (read-only, CI): projection ≠ latest snapshot; replay ≠ To; `todo` left; `custom` fails on
  generated states; chain exists but the view does not reference it; entry missing a scanned definition.
  Warns on transform hash changes.
- `checkViewMigrations(views)` test helper from `@kronor/dtv/migrations` (secondary; does not work where jest
  mocks dtv, as in finance).

## Phases

1. **Two-stage decoding** — codecs, `Undecoded*` types, JSON-level format steps + `definitionRevision` step,
   `decodeViewData`/`encodeViewData`, one read pipeline in the manager, `retainedViews`, per-view isolation,
   URL envelope, static validation, reset notice.
2. **View-level migrations core** — projection, snapshot types, builder + type tests, op implementations,
   chain execution in `decodeViewData`, `View.migrations`, `viewMigrations` runtime section, dev assertion,
   stale-chain handling.
3. **CLI** — Vite-based loading (spike against finance first), `migrate`, `check`, code generation, docs.
4. **Follow-ups** — persisted sorting on top, transform warnings, `squash` / `minSupportedRevision`,
   query-time exclusion of stale data-driven values.

## Known limits

- Transform and `custom` control changes are invisible; `check` warns, authors use `migrate --manual`.
- Data written while a stale chain was deployed carries an older stamp with newer shape. CI `check` guards it.
- Renaming a definition whose instances use derived ids (`…-${orderId}`) does not migrate those instances.
- Instance ids must be unique across all apps sharing one user's store.
- Out of scope, observed in finance: per-order instance ids (`cash-settlement-line-list-${orderId}`) grow the
  user-data blob without bound.

## Decisions log

- Codecs: in-house. Wiring: `view({ migrations })`. `todo()`: type error + check failure.
  CLI loading: CLI primary (Vite), test helper secondary.
- Defaults: reset toast per view; stale chain resets in prod; chains optional; keep `columnOrder`;
  `UserDataJson` stays exported (`onLoad` widens to `unknown`); snapshots kept until `squash`.
- From the finance survey: no item values in projections; no destructive validation of data-driven values;
  definition id ≠ instance id; entry calls factories with placeholders; `--manual` revisions.

## Phase 1 — as built

Modules:

- `framework/decoder.ts` — in-house decoders (`object` keeps unknown fields, `withDefault`,
  `arrayDroppingInvalid`, `recordDroppingInvalid`, `taggedUnion`, `lazy`), issues with paths. No encoders:
  the decoded form is JSON, so writing it is `JSON.stringify`.
- `framework/user-data-undecoded.ts` — `UserDataWithUndecodedViews`, `UndecodedViewData` and nested types,
  their decoders, `UserPreferences`, `BASELINE_DEFINITION_REVISION`.
- `framework/user-data.migrations.ts` — user-data-level steps are JSON → JSON; new step `REVISION_2026_10_25`
  stamps `definitionRevision: 1`. The leaf-ADT step is now the identity: non-tagged leaf values decode as
  `legacy` and are resolved per view.
- `framework/user-data.ts` — `decodeUserData` (stage 1), `decodeViewData` / `encodeViewData`, `decodeViews`,
  `readUserData`, `encodeUserData` (layers stored < retained < decoded; never replaces a newer
  `definitionRevision`). `UserData.retainedViews` replaces `mergeViewsJson` / `baseViews`.
- `framework/filter-form-state.ts` — `decodeFilterState` (reports `resetFilterIds`) / `encodeFilterState`.
- `framework/saved-filters.ts` — `decodeSavedFilter` / `encodeSavedFilter` (replace `*SavedFilterJson`).
- `framework/filter-sharing.ts` — URL envelope `{ view, rev, state }`; App opens the named view.
- Manager: one read path (`readUserData`) for local, remote and storage events; reset toast
  (`viewResetsToToast`) and one write after resets; read-only on a remote or (later) local copy at an
  unknown format revision.

Deviations from the plan above:

- Static validation in Phase 1 covers custom-operator operators only. Column-id / sort validation needs the
  views (not just filter groups) in the manager, which Phase 2 introduces anyway for migrations.
- Unknown-format remote copies now make the manager read-only even when the local copy is newer (before,
  only the chosen source was checked).
- Removed the unused `createShareableUrlForSchema`.
- Public API unchanged: `UserDataJson` (now also with optional `definitionRevision`) still types
  `onLoad` / `onSave`.

## Phase 2 — as built

- `framework/view-projection.ts` — `ViewProjection` (`definition`, `revision`, `filters`, `columns`),
  `projectView(view, definition, revision)`, `projectionsEqual`. Only table columns are projected.
- `framework/view-migrations.ts` — runtime operations (`MigrationOp`), `viewMigrationChain`, schema side
  (`applySchema`, `checkMigration` — the core of `dtv definitions check`), state side (`applyToViewData`,
  `migrateViewData`, `migrateFilterState` for shared URLs), `resetFiltersChangedSinceSnapshot` (stale chain),
  `previousDefinitions` (renames), `currentDefinitionRevision`.
- `dsl/migrations.ts` — typed `defineMigration(from, to, m => [...])` and `defineViewMigrations(baseline,
  migrations)`, exported from `DSL`; `UndecodedFilterFormStateFor<Snapshot>`. Type errors read as
  `DslTypeError` messages (rename of a different shape, keep of a state that no longer fits, non-exhaustive
  `mapOperators`, `todo`).
- `View.migrations`; JSON views reference `{ "section": "viewMigrations", "key": … }` in the runtime.
- `viewMigrationContext(view)` (logs when the live definition differs from the latest snapshot); App passes
  contexts to the manager (`migrationsByViewId` option); `decodeViews` migrates, resets stale filters, takes
  over data of renamed views (old key removed on write); `encodeUserData` stamps the current revision.
- Shared URLs carry the view's current revision and older ones are migrated on load.

Deviations:

- `mapValues` maps list values (multiselect) element by element; `DROP` removes an element, an emptied list
  clears the leaf.
- `resetSort` has a schema side only until sorting is persisted.
- The manager still takes `filterGroupsByViewId` plus `migrationsByViewId`; column-id validation of stored
  hidden columns was not added (unknown ids are harmless; renames/drops are handled by migrations).

## Phase 3 — as built

- `dtv definitions snapshot [definition] [--manual <reason>] [--renamed-from <old>]` and `dtv definitions check`
  (`src/cli/commands/views.ts`, `src/cli/views/`). Options `--entry` (default `dtv.views.ts`),
  `--migrations-dir` (default `dtv-migrations`), `--vite-config`, `--dtv-import`.
- Loading (`loadProject.ts`): the project's own Vite (`createServer` + `ssrLoadModule`, middleware mode, no
  HMR, no dependency discovery) with its config; projection and checking come from the project's own
  `@kronor/dtv` (`projectView`, `checkMigration` exported from the lib). Verified against finance's
  real view factories (journal, history, prepaid fund) with its Vite 8 config.
- Generation (`generate.ts`) follows the table in the plan, plus: a removed filter that pairs with an added
  one of the same structure (not identical) gets a `todo` suggesting `m.custom(old, new, state => state)` —
  otherwise a rename + field change would be dropped without asking.
- `todo(subject, message)` takes any subject (filters, columns, manual revisions).

Deviations:

- No `dtv.config.ts` dependency: finance's config throws without `HASURA_GRAPHQL_ADMIN_SECRET`, so
  `dtv definitions` takes its own options.
- One migrations directory with a folder per definition, instead of folders next to view sources.
- No `tsx` fallback for projects without Vite; no interactive prompts (stubs are the interface).
- Not done (Phase 4): typegen-scan cross-check of the entry, generated-state tests for `custom`,
  transform-hash warnings, `squash`.

## Migrations next to their views (after Phase 3)

- A view that uses its migrations imports them, so `dtv definitions` finds the folder whose index module exports
  the very chain the view has (identity, through the same Vite server) among all `**/dtv-migrations/*`
  folders. Moving a folder only needs the import updated.
- A view that does not use them yet: the `dtv-migrations/<definition>` folder (ambiguity is an error);
  a new one gets that folder next to the view's source file, found with typegen's scanner (`--scan`,
  default `**/*.{ts,tsx}`), or under `--migrations-dir` when the source is not found (JSON views,
  computed ids).
- `check` additionally reports views using another definition's migrations or a chain outside a
  `dtv-migrations/<definition>` folder, and warns about folders no view uses.

## Discovering views (after Phase 3)

- No entry module: `dtv definitions` reads `scan` and `definitions` from `dtv.config.ts`, finds the modules calling
  `DSL.view`, and with the project's TypeScript the exports that are views or return one. Factories are
  built with arguments made up from their parameter types, minimal and contrasting; their projections
  decide (`src/cli/views/definitions.ts`): filters must not differ, an id may only gain a suffix (the
  minimal id is the definition id), columns are united.
- `definitions.factories` configures the exceptions: `definition` (ids computed from arguments) and `args`.
- `schema` may be a function, called by `dtv typegen` only.
- Measured on finance: 175 definitions found, the only configuration needed is the history view's
  definition id. All factories build with made-up arguments; arguments never change filters.
- Loading also bundles dependencies for SSR (CommonJS named exports) and provides jsdom globals
  (modules reading `window` at import).

## Command names (after Phase 3)

Renamed: `dtv views migrate` → `dtv definitions snapshot` (it snapshots definitions and writes the migrations
their changes need; user data is migrated at runtime), `dtv views check` → `dtv definitions check`, and the
`views` section of `dtv.config.ts` → `definitions`. Earlier sections of this plan keep the names of their time.

## Scenario tests

`src/cli/definitions/scenarios/` runs `dtv definitions snapshot` and `check` on throwaway projects (real view
modules, the project's TypeScript discovering them, generated and wired files, TypeScript checking them) and
then dtv's runtime on user data stored before each change. Modules are evaluated by Jest instead of Vite
(Vite loading is covered by runs against finance). 25 scenarios: views coming and going, filter changes
(added, removed, renamed alone and in pairs, look-alike renames, a user migration that falls short, text to
custom operator, field changes, operators removed and added, a range gaining a bound) and the data's life
(several revisions, newer data, unsnapshotted changes, derived ids, view renames, manual enum renames,
column renames, shared URLs). They run with `npm run test-unit:cli`.

## Later changes (after Phase 3)

- `snapshot` wires views up itself (import and `migrations: …` in the `DSL.view` call), and `--renamed-from`
  rewrites the import; it prints the lines only where it cannot.
- A filter removed and exactly one added with the same definition, one to one, is a generated
  `m.renameFilter`; look-alikes that are not one to one each get a `todo`.
- Values cleared by `mapValues` (`DROP`) or `mapOperators` (`null`) are reported like resets.
- Up-to-date views are counted, not listed, when all are snapshotted.
- `dtv definitions` builds factories with console output dropped; the CLI's module building is in
  `src/cli/definitions/project.ts`, shared with the scenario tests.
